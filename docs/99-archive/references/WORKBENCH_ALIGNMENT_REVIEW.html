LLL 的本体先对齐清楚

LLL 不应该继续被理解成“任务面板”或“网页版 Claude”。它更接近一个运行在本地电脑上的学习工作台：真实执行发生在 Claude Code 终端，LLL 负责项目组织、过程观察、结果整理、记忆积累和 Agent 调度。

Local Workbench, Not SaaS

它是什么

本地学习工作台 用户在本机配置好 Claude Code 后即可使用，不依赖云部署。
项目制学习容器 一个主题是一个项目，允许继续拆出子项目递归深挖。
Agent 编排与记忆系统 Agent 不是抽象概念，而是面板里可见、可调用、可追溯的岗位。

它不是什么

不是云端 SaaS 没有账号体系、团队协作、远程权限和多租户这些主线。
不是聊天容器 聊天只是会话形态之一，真正的核心单位是学习项目。
不是假终端 LLL 不能遮蔽 Claude Code 的真实过程，用户就是要看到它。

成功标准

用户第二次还愿意回来 不是一次能跑通，而是主题能持续积累。
学习轨迹可回看 能看到项目树、追问历史、练习产物、总结演化和记忆变化。
Agent 是真岗位 每个 Agent 有固定职责、前驱输入、目标文件和行为规则。
主面板尽可能大 学习阅读、编辑和思考区应当成为绝对主视觉，Agent 面板只做辅助支持。

一句话版本

LLL = 本地项目树 + 真实 Claude Code 终端 + 五段式学习流 + 可视化 Agent 面板 + 持续增长的学习记忆。

一个学习任务就是一个项目文件夹

为了支持知识组织、继续追问、专题拆分、Agent 协作和记忆沉淀，LLL 的基本单位不应该是“单次请求”，而应该是“项目”。项目天然支持树状结构，所以非常适合你的学习方式。

Folder-First

侧栏应展示什么

推荐系统 父项目，负责主题总图、总目标、总记忆和最终总总结。
Intro / Explain / Practice / Extend / Summary 固定五段式板块，任何项目都具备。
Subprojects 专题深挖入口。
用户协同过滤 这是一个完整子项目，不是父项目里的一个零散页面。
图推荐 / 排序学习 / 冷启动 未来都能继续递归挂在父项目下。

为什么项目树比聊天列表更合适

聊天列表 项目树
按会话组织，知识容易散 按主题和子主题组织，天然支持长期学习
不适合挂练习和总结 每个板块都能承载练习、图谱、反思、总结
追问历史容易和最终知识混在一起 会话层与知识层可以分开保存
Agent 很难知道上下文边界 Agent 可以直接围绕项目文件路径读取和写入

五段式不是 UI 标签，而是学习骨架

这五个区不是随便摆一排 tab。它们应该是每个项目都继承的固定结构，用来约束 Agent 行为、文件输出、前驱依赖和用户预期。

Fixed Learning Zones

Intro

负责勾起兴趣、建立问题意识、连接已有知识，不讲太满。

  • 为什么值得学
  • 它解决什么问题
  • 3 个带钩子的进入问题

Explain

结构化讲解区，最适合 MECE + 第一性原理驱动的知识拆解和关系图谱。

  • MECE 拆解
  • 概念关系图
  • 误区与边界

Practice

通过受约束任务逼出产出，强调少量 AI 或不借助 AI。

  • 任务单
  • 提交物
  • 复盘与反思

Extend

高维思考区，只给关系脚手架，不直接给最终答案。

  • 因果关系
  • 结构组成关系
  • 优先级关系 / 同构关系

Summary

用户主导的可编辑总结区，必须可持续改写，不能被一次运行覆盖。

  • 真正学会了什么
  • 还没吃透什么
  • 下一步学什么

默认前驱关系

Intro → Explain Explain 需要继承 Intro 的问题意识和动机。
Explain → Practice Practice 任务依赖已建立的结构化理解。
Explain + Practice → Extend 只有当你既理解又做过，Extend 才有高维度意义。
全部板块 → Summary Summary 是汇总层，不是即时生成层。

产品约束

Practice Agent 不能抢做作业 它设计任务、限制条件、评价标准，但默认不代替你完成练习。
Extend Agent 不能把答案直接端上来 它要引导你自己构建关系认知，而不是直接输出高层结论。
Summary 不能被会话原文覆盖 会话内容可以提炼进 Summary，但不能直接等于 Summary。

点击 Agent 后，真实发生什么

这里是最关键的设计决定之一：LLL 不应该在网页里模拟“AI 正在执行”，而是应该直接拉起一个真实 Claude Code 终端，让用户看到原始执行过程，同时把输出结构化回流到面板。

Real Terminal, Real Trace

调用链条

1. 用户选择 Agent 例如在“Explain”板块点击 Explain Agent。
2. LLL 解析前驱节点 收集 intro/output.md、项目记忆、当前项目信息和本次目标。
3. LLL 构建提示词 提示词里包含 Agent 身份、前驱文件路径、行为准则、输出规范、目标文件路径。
4. 真实 Claude Code 终端被拉起 自动把准备好的提示词送进去，用户能直接看到 CLI 反馈。
5. 输出回流到面板 原始终端输出进入 runs，会话结果进入当前板块文件，整理后内容展示在右侧阅读面板。

提示词拼装应该包含什么

Agent: Explain Agent
Project: recommender-systems / user-collaborative-filtering
Zone: Explain

Predecessor files:
- projects/.../project.md
- projects/.../memory/project-memory.md
- projects/.../intro/output.md

Behavior rules:
- use MECE + first-principles structured explanation
- produce concept relations and misconception boundaries
- do not overwrite summary files

Output targets:
- explain/output.md
- explain/map.mmd
- runs//result.md

为什么不能做成“隐藏执行”

因为你的核心体验之一，就是学习过程中能够看到 Claude Code 的真实反馈。这个过程本身既能提供透明度，也能帮助用户感知 Agent 的思考方式、读文件范围、失败原因和修改轨迹。LLL 的职责不是遮掉这个过程，而是把这个过程组织得更好。

追问机制必须是追加式时间线

如果用户已经在 Claude Code 终端里聊起来了，那么继续追问是自然行为。LLL 不能把后续回复覆盖掉前面的内容，而应该把它们作为同一 Session 下的新 Turn 追加进历史时间线。

Append-Only Session

面板应该如何显示

Turn 01 · 用户 “先用适合入门者的方式解释用户协同过滤是什么。”
Turn 01 · Claude 结构化回复，并引用当前项目中的 Intro 前驱节点。
Turn 02 · 用户追问 “那它和基于内容推荐最本质的区别是什么？不要直接给答案，给我比较框架。”
Turn 02 · Claude 继续回复，并被追加到历史下方，不覆盖 Turn 01。
面板整理动作 用户可以把 Turn 02 的部分内容提炼进 extend/relation-notes.md，但会话原文依然保留。

设计规则

规则 1 一个被拉起的 Claude 会话就是一个 Session。
规则 2 每次用户输入算一个 user turn，每次 Claude 一轮完整回复算一个 assistant turn。
规则 3 面板展示按时间追加，不允许“用最新结果替换整个会话结果”。
规则 4 项目知识文件与追问原文分层保存：原文进 runs，会话提炼进项目板块。

推荐的会话文件结构

runs/
  2026-06-08-explain-agent-session-01/
    session.json
    transcript.ndjson
    turns/
      001-user.md
      001-assistant.md
      002-user.md
      002-assistant.md
    artifacts/
      explain-output.md
      extend-prompts.md

多 Agent 不该像魔法，而该像岗位

Agent 不应该只是“再来一个模型按钮”。对 LLL 来说，更合理的方式是把 Agent 设计成项目中的角色岗位：有身份、有准则、有能做和不能做的事，有明确读写文件路径。但在视觉层面，Agent 面板应当始终让位于学习主面板。

Main Learning Panel First

推荐的工作台比例

项目树

保持窄而稳定，只负责导航，不争夺阅读注意力。

推荐系统 项目总览、板块导航、子项目入口。
用户协同过滤 当前专题子项目。
五段式板块 Intro / Explain / Practice / Extend / Summary。

学习主面板

这是工作台的绝对主角。阅读、编辑、思考、比较、批注都应该优先发生在这里。

为什么这里必须最大 因为用户真正花时间的是看内容、做练习、写总结、建关系，而不是盯着 Agent 控制器。Agent 再强，也只是辅助学习的执行轨道。
上半区 当前板块内容，例如 Explain 的结构化讲解、Practice 的任务单、Summary 的可编辑总结。
下半区 会话时间线、追问历史、从 Turn 提炼到项目文件的内容对照。
核心交互 高亮前驱节点、局部批注、把当前回复提炼进指定文件、直接编辑 Summary。

Agent 侧轨

应当做成辅助轨道、可折叠侧栏或临时展开面板，而不是主阅读区。

身份与规则 当前 Agent、行为边界、输入文件、目标文件。
动作按钮 启动 Claude Code、继续追问、提炼进板块文件、更新记忆。
建议形态 默认收起或窄栏显示，需要时展开，避免长期压缩学习内容宽度。

Agent 面板应该承载什么

身份 例如 Explain Agent、Practice Agent、Memory Agent。
当前板块 Agent 当前服务 Intro、Explain、Practice、Extend 或 Summary。
前驱文件 清楚显示本次会读哪些路径，而不是暗箱操作。
动作与产物 启动终端、继续追问、写入目标文件、回流面板。

Agent 面板不应该承载什么

不应抢占版心 如果 Agent 区域长期和学习区等宽，学习体验会被控制逻辑稀释。
不应成为主叙事区 主叙事应该是知识内容、练习任务、关系笔记和总结，而不是按钮和状态。
不应长期常驻细节噪音 过多状态、日志和参数会打断学习沉浸感，应该按需展开。

建议的 Agent 岗位

Agent 主要职责 默认行为边界
Intro Agent 勾起兴趣、建立问题意识、连接已有知识 不直接进入大段讲解
Explain Agent 用 MECE + 第一性原理方法结构化解释知识 不覆盖 Summary
Practice Agent 设计少 AI 或无 AI 的任务和标准 默认不替用户完成练习
Extend Agent 提出高维关系问题和思考框架 默认不直接给终局答案
Summary Agent 辅助整理总结、列出可编辑纲要 不能替代用户最终主导权
Memory Agent 更新项目记忆和用户长期记忆 不能静默篡改学习事实

记忆系统要增长，但不能偷偷接管你

记忆系统不是把过去所有内容机械堆起来，而是逐渐更懂这个用户怎么学、哪里卡住、哪些解释有效、哪些任务太简单或太难。它的价值是个性化，不是替代用户判断。

Learner Memory, Not Hidden Bias

两层记忆结构

全局记忆 记录学习目标、惯用学习方式、偏好表达风格、长期能力变化。
项目记忆 记录在当前主题下已经会什么、总混什么、哪些例子最有效、下一步最该补哪块。

记忆如何反哺系统

调提示词 Explain Agent 会知道这位用户更适合先看类比还是先看结构。
调练习难度 Practice Agent 会减少无效重复，调整任务强度。
调 Extend 提问方式 如果用户已经习惯因果思考，系统就可以多给同构关系提示。

最小记忆示意

memory/
  learner-profile.md
  learner-state.json

projects/.../memory/
  project-memory.md
  project-state.json

learner-state.json
{
  "preferred_explanation_style": ["analogy-first", "structure-second"],
  "ai_usage_preference": "practice-should-be-constrained",
  "recurring_gaps": ["high-level relation building"],
  "current_focus_topics": ["recommender systems"]
}

关键约束

记忆系统只能帮助 Agent 更贴近用户，不能在用户不知情的情况下静默改变项目结论、Summary 事实或练习完成判定。换句话说，记忆负责“更懂你”，不负责“替你做主”。

落地前的最终对齐清单

这一页不是新想法，而是把前面所有页收束成可以决策的清单。只要这些点对齐，后面就可以比较稳地切进实现和迭代切片。

Implementation Gate

我们已经基本对齐的点

项目是文件夹，不是聊天 父项目和子项目都用同一骨架。
五段式是固定结构 每个项目都必须有 Intro / Explain / Practice / Extend / Summary。
Agent 启动真实 Claude Code 终端 不是网页里的假执行过程。
追问必须追加，不覆盖 会话层与知识层分离。
记忆系统分层 有全局记忆，也有项目记忆。

实施前还要确认的点

终端接管方式 是 PTY 挂载到本地窗口，还是先以系统终端窗口为主、面板只做追踪？
Summary 编辑策略 是原地编辑 Markdown，还是双栏“原文 / 整理稿”模式？
会话恢复规则 终端关闭后，再追问是恢复同一 Session，还是新建 Session 并挂到同一板块？
记忆更新时间点 每次 Agent 运行后都更新，还是只有在用户确认后才写入记忆？
第一期最小实现范围 建议只先做单项目、单终端会话、Explain/Practice 两个 Agent 和追加式 Session。

推荐的第一期切片

如果你要我建议一个最稳的第一刀，我会推荐：先做项目树、Explain Agent 终端直连、追加式 Session 历史和可编辑 Summary。因为这四个一旦成立，整个工作台的主框架就开始成型了，后面的 Practice / Extend / Memory 都能顺着挂上去。
