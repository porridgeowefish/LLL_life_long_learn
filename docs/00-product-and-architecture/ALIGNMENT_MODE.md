# 对齐模式

状态：active
负责人：project maintainer
最后审阅：2026-07-05
事实源：本文定义 LLL 在实现前如何使用对齐文档。

## 当前模式

LLL 的对齐材料使用 Markdown 作为可编辑交接格式。

```text
对齐讨论 -> Markdown 对齐文档 -> 迭代文档 / 代码实现
```

HTML 原型或评审页可以继续作为历史视觉参考保留，但不再作为用户主要编辑的对齐合同。

## 为什么用 Markdown

优先使用 Markdown 对齐，因为：

```text
用户可以直接在仓库里修改
AI 可以读取精确文本和 git diff，不依赖浏览器状态
决策可以被 git 审查
认同 / 需修改 / 不采用 / 待决定 项离迭代文档更近
不需要下载 HTML，也不需要把交互状态重新嵌回 HTML
```

## 文档格式要求

每份对齐文档应包含：

```text
状态
负责人
最后审阅时间
事实源说明
如何编辑
决策项或决策表
开放问题
AI 交接规则
```

每个决策项应有稳定 ID 或稳定标题，并使用以下状态之一：

```text
accepted  = 认同
revise    = 需修改
rejected  = 不采用
pending   = 待决定
```

状态值保留英文，是为了方便 AI 和脚本稳定识别；正文和反馈应优先使用中文。

## AI 交接规则

当用户说已经修改对齐文档后，下一轮 AI 必须：

```text
1. 先读取 Markdown 对齐文档。
2. 将 accepted 项视为已确认方向。
3. 对 revise 项，必须结合用户反馈改写后再进入实现。
4. 忽略 rejected 项，除非需要引用其理由说明边界。
5. 只有 pending 或互相冲突的项阻塞执行时，才向用户追问。
6. 在可行时，同一轮同步更新迭代文档和代码。
```

新工作不要再要求用户编辑、下载或交接 HTML 对齐文件。
